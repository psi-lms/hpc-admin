```sshconfig
Host thanos thanos.psi.ch
  HostName thanos.psi.ch
```

```
uid=1001(aiida) gid=1002(aiida) groups=1002(aiida),27(sudo)

```

`aiida` has sudo via group membership but **not** passwordless. Ubuntu caches the sudo timestamp per-TTY, so `ssh host 'sudo ...'` and `pdsh ... 'sudo ...'` can never work. ### The container is only half of a psql_dos profile

`core.psql_dos` splits a profile across **two** filesystems:

| | lives on | protected by |
|---|---|---|
| disk-objectstore container | `/nfs/aiida_data` | filer snapshots (10 min), plus whatever backs up the filer |
| PostgreSQL database | `/home/postgres/postgresql/14/main`, local disk | **nothing, for these four profiles** |

`mc3d-pbesol-v1-prod`, `aiida-arch_final`, `aiida-arch_t1` and `aiida-presto-8` are databases on thanos's local disk with no cron entry and therefore no `db.psql` anywhere. A disk-objectstore container without its database is content-addressed blobs with no node metadata, no links, no provenance. So "those are fine" holds for the bytes, not for the profiles.

Also: `/nfs/nfsbackup` and `/nfs/aiida_data` are **both exported by 129.129.160.237**. One filer holds the live NFS data and the thanos backups. Confirming that the filer itself is backed up or replicated off-box is the single highest-value question to put to PSI storage.

### Correction to session 4

`mc3d-relax/prod-zmq` shares the same **database** (`mc3d-relax-prod`) as well as the same repository as `mc3d-relax/prod`. It is a duplicate profile entry with a different broker config, not a second dataset. Backing up `prod` covers it completely. Session 4 said "two separate databases"; that was wrong.

### `fermisurf/main` is not a scheduling gap, it is a data integrity failure

```

    raise RuntimeError(
RuntimeError: There are objects referenced in the database that are not present in the repository. Aborting!
```

The 2026-08-20 run crashed inside `verdi storage maintain`. The profile has database rows referencing repository objects that do not exist. Its `backup.log` contains neither `Success` nor `Failure`, so `aiida-backup-checker.py` (which only greps for those two words) prints **no row at all** for fermisurf: a silent omission, not a red mark.

This has to be understood before the OS upgrade. Its last good backup is 2026-08-19 (`db.psql` 13.6 GB).

### The coverage gap is a crontab choice, not a tooling limit

`aiida-backup.sh` already auto-detects every profile when `-p` is omitted:

```bash
profiles=$(verdi profile list | awk 'NF && !/Report:/ {gsub(/^\*/, ""); print $1}')
```

All 13 cron lines pass `-p <single-profile>` explicitly. Dropping `-p` would back up every profile in each project. That is the direct answer to "is multiple profiles per project a problem": the tool handles it, the crontab opted out, and nothing warns you when a new profile appears.

### Two more defects in the backup setup

- Four projects (`sssp-tests`, `sssp-project`, `mc3d-source`, `mc3d-electronic`) have **two cron entries each, all firing at `0 0 * * *`, all writing `$ROOT/<project>/backup.log`**, which the script opens with `tee` (truncating). Both runs currently survive by luck of timing. One line per project with no `-p` removes the race and closes the coverage gap at the same time.
- `aiida-backup-checker.py` reports only on `Success`/`Failure` strings, so a crash reports as absence. It should assert one row per expected profile.

## 2026-08-20, session 6: crontab replacement drafted

`crontab/` holds a replacement crontab taking coverage from **13 profiles to 32**, plus a read-only pre-flight and install instructions. Not installed; handed over for JG to run.

Two structural changes beyond adding profiles:

- **One line per project, profiles as a space-separated `-p` list.** `aiida-backup.sh` derives its log path from the project name and opens it with a truncating `tee`, so two entries for one project race on `$ROOT/<project>/backup.log`. Four projects already had two entries at `0 0 * * *`; adding three more `sssp-tests` entries would have made five concurrent writers on one file. A single invocation loops the profiles sequentially into one log.
- **Staggered start times, largest project first**, 15 min apart across 00:00 to 04:00. All 13 previously fired simultaneously at 00:00, issuing ~200 GB of `pg_dump` plus the NFS writes at once.

Deliberately excluded: `alps_run` x3 and `mc3d-pbesol-v1/prod` (containers on NFS by design, filer-snapshotted, DBs covered by `pg_dumpall`).

Absent from the list handed over and therefore left out, flagged in case the omission was accidental: `kristjan_tests/sssp-sqlite` (88G), `sirius_tests/presto` (3.7G), `sirius_tests/qe_tests` (710M).

Open risk: the script sources `$aiida_venv_dir/$project/bin/activate`, so every newly-added project needs a venv named exactly after it. `crontab-preflight.sh` checks that, and that each named profile exists in the project's `config.json`, before anything is installed.

### One-shot runner for a final pre-upgrade backup

`crontab/run-all-backups.sh`: runs the same 17 invocations sequentially, now, instead of on a schedule. No mechanism exists to fire a user crontab on demand, and editing the schedule means remembering to restore it.

Defaults to `KEEP=6` rather than the cron's 3, so the pre-upgrade snapshot survives the next few nightly runs. Per-project logs under `~/backup-run-<timestamp>/`, a status table at the end, and a recorded list of every `last-backup` target so the pre-upgrade snapshot can be identified afterwards. It judges success from the log contents rather than the exit code, because `aiida-backup.sh` exits 0 even when `verdi` inside it fails.

### Reboot done; checker script unaffected by the crontab change

`aiida-backup-checker.py` reads `/nfs/nfsbackup/aiida_thanos/<project>/backup.log`, not the cron stdout logs under `~/scripts/aiida-backup-script/`, and it has no notion of time. It greps whatever the last run wrote. So neither the changed schedule nor manual runs interfere. Project discovery is `os.listdir(BACKUP_DIR)`, so new projects appear automatically once backed up.

Consolidating to one cron line per project **fixes** a checker bug: the four projects that previously had two entries racing on one truncating `tee` could report only one profile, or a mangled mix.

Remaining weaknesses, both more significant at 32 profiles than at 13:

- Only `Success`/`Failure` are matched, so a crash yields **no row at all** rather than a red mark. This is exactly how `fermisurf` went unnoticed.
- `open(log_file_path)` has no error handling and the only guard is `EXCLUDE_DIRS = ["first-hero-run-backup-2024"]`, so any directory under `BACKUP_DIR` without a `backup.log` crashes the whole script.

Stale after the change: `aiida-backup-cron_*.log` in `~/scripts/aiida-backup-script/`. The new crontab writes `aiida-backup-<project>.log`. Harmless orphans.

Never run a manual `verdi storage backup` while the nightly cron can fire on the same profile. Either suspend the crontab for the duration, or finish before the first cron slot. ### On corruption

No source corruption. The `FileExistsError` on `packs/N.lock` is disk-objectstore's pack lock refusing a second writer, which is the protection working. An interrupted pack leaves orphaned bytes past the last recorded offset (unreferenced by the SQLite index, reclaimed by a later repack) and possibly a stale lock file. Loose files are removed only after their pack commits, so nothing is lost in between.

One caveat to keep in mind: the SQLite index for these two profiles sits on NFS, where SQLite's advisory locking is unreliable. Two processes on one index is the only mechanism here that could genuinely bite; exposure was small because the second process died at lock acquisition before writing.

The backup destination is gated: `live-backup` only becomes a snapshot if the final rename succeeds, which is exactly what failed for `arch_final`. A half-written staging directory cannot pass itself off as a good backup.

**`verdi storage integrity` is a stub with an empty body** in `cmd_storage.py` and does nothing. The real check is disk-objectstore's own CLI, on the three containers that had two writers:

**Two file-permission traps hit on the way**, same root cause each time, and worth remembering: a command run under `sudo -u <service>` or executed *by* a service writes as that service's user.

### Speed

`-m upgrade` (pg_upgrade, copy mode) sustained **~810 MB/s** for 25 minutes, moving 1.5 TB in roughly half an hour. The default `dump` method would have rebuilt every index on a 1.5 TB cluster instead, which is a many-hour job. `--link` was deliberately avoided: it would have been near-instant but would have consumed the 14 cluster, destroying the only rollback available once the OS had moved.

Progress was tracked with a `df`-based loop rather than `du`, since `du` walks the whole tree on every poll and gets slower as the target grows, while `df` is O(1):

```bash
TARGET=$((1500*1000**3)); START=$(df -B1 --output=used /home|tail -1); PREV=$START; PREVT=$(date +%s)
while sleep 30; do NOW=$(date +%s); USED=$(df -B1 --output=used /home|tail -1); DONE=$((USED-START));
  D=$((USED-PREV)); DT=$((NOW-PREVT)); RATE=$((DT>0?D/DT:0)); ETA=$((RATE>0?(TARGET-DONE)/RATE:0));
  printf '%s copied %9s  rate %9s/s  eta %02d:%02d\n' "$(date +%H:%M:%S)" "$(numfmt --to=iec $DONE)" \
    "$(numfmt --to=iec $RATE)" $((ETA/3600)) $(((ETA%3600)/60)); PREV=$USED; PREVT=$NOW; done
```

### Statistics

`pg_upgrade` does not carry over planner statistics, so they have to be rebuilt or every query plans against empty stats. **`pg_upgradecluster` handled this itself**, running `vacuumdb --all --analyze-in-stages` through all three passes at the end. No separate step needed.

## 2026-08-25: Phase 7, venv rebuilds

### `aiida-project` cannot do this itself

`aiida-project` 0.7.0 (the release that switched `VenvProject` to `uv`, merged 2025-10-01, tagged the next day) has only `init`, `create` and `destroy`. `create` always makes a **new** project and `destroy` removes the project directory as well as the venv, which would take `.aiida/config.json` with it. Neither can recreate a venv for an existing project.

So the venv is built with `uv` and the two lines `aiida-project` injects into `bin/activate` are reproduced by hand:

```
deactivate () {
    unset AIIDA_PATH          <- inserted as the first line
...
export AIIDA_PATH=<project_dir>
eval "$(_VERDI_COMPLETE=bash_source verdi)"    <- appended at the end
```

Without those, `cda` would activate a working venv pointing at `~/.aiida` instead of the project's profiles: a silent wrong-profile failure. The script verifies the patch applied and aborts if not, because `uv` writes its own activate script and the `sed` anchor could stop matching.

The per-project registry at `~/project/.aiida_projects/venv/<name>.json` records `venv_path` and `project_path`, and the rebuild keeps both, so **no registry update is needed**. It also records the anchor as `shell_deactivate_mapping.bash = "deactivate () {"`, confirming the sed target.

### Finding the editable sources: three dead ends and the answer

Most projects install packages editable from local git checkouts, and `pip freeze` renders those as `-e git+<remote>@<sha>#egg=<name>`. **That describes the remote, not where the source is**, so the freeze cannot answer the question.

* `<venv>/src/` (pip's default for `pip install -e git+URL`): **no venv has one**. Nothing was ever cloned by pip.
* `<project>/git-repos/`: only 6 projects. Others use `git/`, and the name comes from `aiida_project_structure` in the config, so it varies.
* `.egg-link` / `__editable__*.pth`: absent. Hatchling and flit write a plain `<package>.pth` instead.

The answer is **`<dist-info>/direct_url.json`** (PEP 610), which pip writes for every install and which gives the installable root directly:

```json
{"dir_info": {"editable": true}, "url": "file:///home/aiida/project/pseudo-opt/git/aiida-sssp-workflow"}
```

`rebuild-venv.sh` reads that, falling back to harvesting `.pth`/`.egg-link` contents (stripping a trailing `/src` for src-layout packages) for anything older.

### Scope across all 20 projects

Every editable in every project resolves to a directory on disk. Layouts are inconsistent: `git/`, `git-repos/`, `epfl-backup/code/`, `jupyter/...`, and `sssp-project` keeps checkouts in the project root.

**Checkouts are shared across projects**, so those directories must not be tidied up:

* `mc3d-relax-so` installs `aiida-wannier90-workflows` from `mc3d-electronic/git-repos/`

## A. The netplan change


**Not about iDRAC.** The management network (`192.168.8.x`) is unreachable from both the workstation and thanos, so the console stays unavailable pending PSI. Separate request.

**Scope, after Ali's input (2026-08-24):** preserve the current setup and both IP addresses. The only change is replacing a deprecated keyword so the config keeps working on Ubuntu 24.04. Nothing is consolidated, nothing is deleted.

### Background

`netplan` describes network settings, and reads **every** file ending in `.yaml` in `/etc/netplan/`, merging them. `*.bak` is ignored.

```
00-installer-config.yaml            read     static 129.129.240.32, gateway4, 8.8.8.8
backup_00-installer-config.yaml     READ     dhcp4: true on all four NICs
backup_01-network-manager-all.yaml.bak   ignored
```

The second file is a copy someone left in place roughly two years ago, from before PSI issued static addresses. Because it ends in `.yaml`, netplan has been treating it as live configuration ever since. That is where `129.129.240.225`, PSI's nameservers (`129.129.190.11`, `129.129.230.11`) and the `psi.ch` search domain come from. Ali confirmed it is deliberate to keep, so it stays.

### The one real problem

`00-installer-config.yaml` sets the default route with `gateway4:`. That keyword is **deprecated and no longer honoured by the netplan in Ubuntu 24.04**, which expects `routes:`.

Today it does not matter, because the DHCP file supplies a default route too. After the upgrade the static file would silently stop contributing one, leaving the machine dependent on DHCP alone for reachability. Since there is no console, that is not a dependency worth accepting.

`routes:` works identically on 22.04, so the change is safe to make now and correct afterwards.

Note that **deleting the DHCP file instead would be the worst option**: it removes the fallback route while leaving the deprecated keyword, so on 24.04 there would be no default route at all, and internal PSI names would stop resolving.

### What changes

```diff
-      gateway4: 129.129.240.1
+      routes:
+      - to: default
+        via: 129.129.240.1
```

Both addresses stay. DNS stays. The second file stays.

---

### Procedure

Three terminals:

- **T1** on thanos, inside `tmux`, where the change happens
- **T2** a second, separate connection to thanos, for checking
- **W** your workstation

Open T1 and T2 **before** starting. The terminal running `netplan try` is the one that may go silent.

### Step 1 [W] Copy the new file over

```fish
rsync -avz ~/notes/2026/thanos-upgrade/to-thanos/ thanos:~/scripts/upgrade/
```

Nothing is applied by this.

### Step 2 [T1] Start tmux

```bash
tmux new -s netplan
```

If the SSH connection drops, the work continues and you reattach with `tmux attach -t netplan`.

### Step 3 [T1] Record the current state, to compare against

```bash
ip -br a show enp129s0f0np0
ip route
resolvectl status | grep -A4 'Link 4'
```

Expect two addresses (`.32` and `.225`) and two default routes. That is what must still be true afterwards.

### Step 4 [T1] Back up the config

```bash
sudo mkdir -p /var/backups/netplan-$(date +%F)
sudo cp -a /etc/netplan/. /var/backups/netplan-$(date +%F)/
ls -la /var/backups/netplan-$(date +%F)/
```

All three files, somewhere netplan does not read. `/var/backups` is the distro's own directory for this sort of thing, already exists, and is on the root filesystem so it stays put across the upgrade.

### Step 5 [T1] Install the edited file

```bash
sudo cp ~/scripts/upgrade/00-installer-config.yaml.new /etc/netplan/00-installer-config.yaml
sudo chmod 600 /etc/netplan/00-installer-config.yaml
sudo diff /var/backups/netplan-$(date +%F)/00-installer-config.yaml /etc/netplan/00-installer-config.yaml
```

The `diff` is the important line: it should show **only** the comment header and `gateway4` becoming `routes`. Anything else means the wrong file was copied.

`chmod 600` matches the permissions netplan expects; it warns loudly otherwise.

### Step 6 [T1] Syntax check, applying nothing

```bash
sudo netplan generate
```

Parses the config and writes networkd's internal files. **Does not touch the running network.** Silence means good. An error here costs nothing.

### Step 7 [T1] Apply it, with an automatic undo

```bash
sudo netplan try
```

Applies the config, then waits with a countdown. **Do not press Enter.** After 120 seconds of inaction it reverts by itself. That is the safety property: if the change breaks your connection you cannot confirm it, so it undoes itself.

### Step 8 [T2] Check while the countdown runs

```bash
ip -br a show enp129s0f0np0
ip route
resolvectl status | grep -A4 'Link 4'
getent hosts thanos.psi.ch
```

Should be **identical to step 3**: both addresses, both default routes, PSI nameservers, `psi.ch` search domain. This change is meant to be invisible today; visible differences mean something is wrong.

### Step 9 [W] Prove a brand new connection works

```fish
ssh -o ControlMaster=no -o ControlPath=none thanos hostname
```

Those options force a genuinely new TCP connection instead of reusing the multiplexed one, which would succeed even if the network were broken for everyone else.

### Step 10 [T1] Decide

- Steps 8 and 9 match step 3: press **Enter** to keep it.
- Anything differs, or you are unsure: **do nothing** and it reverts.

### Step 11 [T1] Persist and prove it survives a reboot

```bash
sudo netplan apply
sudo reboot
```

A config that works until the next boot is worse than one that never worked, because you would find out mid-upgrade.

### Step 12 [W] After it comes back

```fish
ssh thanos 'ip -br a show enp129s0f0np0; ip route; systemctl --failed'
```

Both addresses, both default routes. `systemd-networkd-wait-online.service` will probably still be failing, as it has for two years; that comes from the two merged configs and is out of scope here.

```bash
sudo cp -a /var/backups/netplan-<date>/00-installer-config.yaml /etc/netplan/
```

### What changed beyond adding profiles

- **One line per project, profiles as a space-separated `-p` list.** `aiida-backup.sh` derives its log path from the project name (`$ROOT/<project>/backup.log`) and opens it with a truncating `tee`, so two cron entries for the same project race on that file. `sssp-tests`, `sssp-project`, `mc3d-source` and `mc3d-electronic` each had two entries at `0 0 * * *` and currently survive on timing luck. - **Consistent log names**, `aiida-backup-<project>.log`.
